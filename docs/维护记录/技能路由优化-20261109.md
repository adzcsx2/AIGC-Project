# 规则与技能路由优化记录

范围：项目规则、十个制作技能入口和元数据、交接条件；既有“补帧”技能保留原样并纳入统一路由。保留全部既有未提交修改；优化前快照见仓库根目录下的 `docs/archive/规则路由优化-20261109-实施前/`。未修改客户端/模型目录/凭据，未提交生成任务。

## 已修正的问题

| 原问题 | 修正位置与行为 |
|---|---|
| 有源视频就转复刻，忽略分析或借风格 | 总导演先判断素材用途；分析走breakdown，保留运动换角才retargeting |
| 角色运动板完成后默认去复刻 | board回到原任务：原创继续原创，复刻继续复刻，只要板则交付结束 |
| 白模预演完成后直接交付费视频链 | huashu仅预演任务完成即交付；已有明确复刻生成请求才接autodl |
| 总导演和专业技能的描述重叠、元数据过于通用 | 十个description明确适用/排除，default_prompt对齐职责，保留其他元数据；隐式调用均开启 |
| 固定15秒、所有图片走MJ、逐段审片的旧默认与新要求冲突 | 清除过时硬性段落；图片按用途，分段按审计，多片段技术检查后交用户审片 |
| 多处技能列表与内部资料被当成新入口 | `skill-routing.md`统一职责和交接；内部资料/历史不作为可调用入口 |
| “继续”可能重启流程或重复提交 | 按当前确认节点/素材状态/task_id/片段版本恢复；区分反馈、确认和新生成 |
| 重要打击的速度变化只是可选、力度不足 | fight/camera/AGENTS/审计模板共同落实快动作→命中短时停/骤慢→回速的默认设计 |

## 带上下文的路由核对

以下是依照最终规则进行的人工场景推演，不是独立模型的路由命中率测试，不调用真实媒体生成。主技能按最终交付物确定，协作只补具体缺口。

| 场景与已有状态 | 应用路由 | 执行边界 | 核对 |
|---|---|---|---|
| “这两个API谁支持尾帧？” | autodl | 只读规则，不进入导演/生成 | 通过 |
| “这个task_id超时了，继续等” | autodl | 恢复同一任务，不重提、不再确认剧本 | 通过 |
| “A打B，做30秒，帮我编动作”尚无动作稿 | workflow主导＋fight | 先补稿供确认，不抢先生图/视频 | 通过 |
| “已确认动作，只改运镜” | camera | 不重写动作或台词，不生成 | 通过 |
| “22秒为什么只见腿？分析并改镜头描述” | camera主导＋breakdown定位 | 只诊断指定区间并改摄影；不全片重审/重抽 | 通过 |
| “台词不变，只补克制表情”已有镜头 | acting | 不改机位、不新增对白/大动作 | 通过 |
| “打击要快、命中时停，写进规则” | 规则维护＋fight/camera方法 | 更新规则，禁止把偏好反馈当付费重做 | 通过 |
| “一张人物图生成正背侧与运动板” | board，使用适用imagegen工具 | 实际生成板；没有视频请求则不生成视频 | 通过 |
| “单独修这张场景图” | visual | 局部图片用途，不误生成多视图板 | 通过 |
| “分段已确认，先做6张衔接图，不要视频” | visual | 仅生成所需图片并交用户审图 | 通过 |
| 原已要求完整视频，用户确认所有边界图说“继续” | workflow→autodl | 归档/校验后提交计划内各段；不重复问费用 | 通过 |
| 只做参考板任务，用户说“这张可以” | board | 归档结束，不擅自开视频任务 | 通过 |
| “保留白模动作和镜头，换我的角色” | retargeting主导；按需breakdown/board；autodl执行 | 保留源动作，禁止原创编招或加切镜 | 通过 |
| “学习这条视频的摄影，为新故事写稿” | workflow＋按需breakdown/camera | 素材为学习参考，不误走保留动作复刻 | 通过 |
| “做空间白模预演，不要正式视频” | huashu＋必要camera | 本地预演，禁止自动提交titim | 通过 |
| “调用Seedance云API”但只装了本地预演技能 | 先核实真实可用服务 | 不把huashu当云API，不虚构接口 | 通过 |
| “第二段重生成，其他别动”已有反馈与确认边界 | workflow＋对应修正技能→autodl | 只重做指定段，用户认可后重合成 | 通过 |
| “替换段可以，重新合成” | workflow安排本地拼接 | 不重新生成、不默认审片 | 通过 |
| “刚才这段补到60帧”源文件明确 | 补帧 | 本地RIFE处理并保留播放速度/原声，不调用生成API，不把插帧当打击节奏重编 | 通过 |
| “修复客户端validate报错” | 代码开发，按需autodl了解接口 | 修改对应代码/测试，不进入创作生成链 | 通过 |
| “精确复刻原动作，但重新编更华丽的招式” | 先核对保留范围 | 两个目标冲突处澄清，不擅自任选并提交 | 通过 |

验证结果：十个制作技能通过skill-creator的quick_validate；全部11个技能的UI YAML、隐式调用、路由覆盖和安装清单哈希检查通过，相关本地链接存在，git diff --check通过。既有“补帧”的中文名称是通用校验器仅允许英文hyphen-case的例外，保留用户指定名称，未改写该技能正文。以上21个案例是人工场景推演，没有调用生成模型测试。

实际路由仍需结合用户上下文执行，不承诺任何措辞都百分百命中；新误路由应修正职责边界，不靠堆更多同义关键词或重复技能。
