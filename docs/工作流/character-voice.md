# 人物档案与声音绑定

依据：用户2026-11-10要求及本轮澄清。人物按作品管理，每人一个YAML；**只有当前剧本要求人物说话时，才需要为他配置声音**。人物仅出镜、没有台词或只有呼吸/吼声等非语言声，不列入配声待办、不要求试听；以后剧本增加说话内容时再配置。接口证据见[本次审计](../验证记录/角色声音-20261110/审计结论.md)。

## 文件与职责

- `projects/<作品>/project.yaml` 的 `characters` 只索引稳定人物ID到 `01-文档/角色/<中文识别描述>.yaml`。改名、换装、不同参考板不能另造一个人物身份。
- 人物YAML保存属性摘要、原设定文档/图片引用及唯一声音选择。`character_id`用于程序绑定；`label`描述“青衣女子”等可辨认形象；`display_name`默认null，可由用户命名，仅供用户识别。
- 剧情中是否喊名字、喊哪个名字/爱称，只由已确认剧本和该镜头提示词决定。不因设置display_name自动加入称呼、对白、字幕，也不把内部ID念出来。旁白若属于独立声线，也单独建立人物/旁白档案。
- 属性未知可空；长篇设定仍由Markdown拥有，不复制成第二份正文。换装和形态变化写为同一身份的变体；是否为不同意识/独立说话者以剧情为准。
- 人物YAML中的路径相对**作品根目录**；声音统一存 `02-素材/音频/角色声音/<人物中文描述>/`，候选、参考和后续对白按语义命名。选中候选只更新引用，不另复制同一音频。
- `materials.yaml`仍拥有资产技术状态和真实API输入绑定；人物YAML拥有音色选择与用户试听确认。两者分别是“这份文件可用”与“这个人采用这个声音”，不能相互代替。`project.yaml`不再复制它们的状态。

## 新角色三视图前置与API绑定

用户2026-11-10补充：新人物包含动物、怪物和其他非人角色，是否说话不影响视觉前置要求。以下适用于新角色进入制作及后续图片/视频API；首次生成三视图本身不要求先有另一张三视图，避免循环依赖。

1. **先识别与建档。** 从当前已确认内容列出每个新角色，沿用`project.yaml.characters`及独立角色YAML，记录外观、身体结构和实际参考。有原图先实看；没有原图则从已确认设定及本片style直接制作三视图，不先在场景里临时设计角色。设定尚待决定时依既有文案确认规则处理，不虚构已确认身份。
2. **先生成独立三视图。** 每个角色一张板，仍仅正面特写、正面全身无头、背面全身，详见 [固定版式](../../.agents/skills/character-reference-board/references/版式与三视图.md)。动物按自身头部、躯干、四肢、尾翼与支撑结构展示，不强套人形站姿、服装或肢体；省头只影响正面身体展示。不得用场景图中的局部裁切或文字描述冒充三视图。
3. **验收、归档与复用。** 按既有图片验收授权实看三视图并确认身份/结构/风格；需要用户选图时等待该节点，已有自主验收授权按原范围执行。三视图存作品`02-素材/人物/`，人物YAML的`visual_references`引用该资产，materials登记真实路径及就绪状态；哈希与确认依据沿用现有审计/制作记录，不新增重复状态表。同身份已有合格三视图直接复用，不重复要求确认或自动重做旧素材。
4. **后制作含角色的场景图。** 场景、首尾帧、衔接图与剧情图以该角色三视图为身份参考，另用环境参考控制空间与光照。不得先在这些图里生成一个临时角色，再仅凭场景图提交下游API。无角色的环境图、简单白模和其他不依赖该身份的已授权工作可继续。
5. **实际请求绑定三视图。** 每个含该新角色的下游图片/视频请求，须在真实支持的身份/图像参考输入里绑定其三视图文件；如为多角色，逐一记录`character_id → 三视图asset ID/路径/SHA-256 → 实际输入槽位`。在已有`required_assets`、`reference_bindings`与提交审计中核对实际文件、图序和英文主体映射；只把板放入目录/清单或在prompt中提到板，不算已经传给API。场景图另负责编排、空间/光照或端点，不能替代三视图身份输入；三视图也不能冒充完整场景首尾帧。
6. **接口不兼容先解决。** 核实当前入口的槽位用途、容量和对多视图板的支持；不从存在图片字段就推定可作为身份参考。只有首尾图而无额外身份参考能力、单图用途不兼容或槽位不足时，标明影响镜段并在准备阶段解决可兼容路线；需更换用户指定模型或放宽此规则时交用户明确决定，不能静默退回仅场景图、塞错字段或宣称已绑定。独立工作照常推进。

已授权制作中的新角色三视图是必要前置，不要求用户另说一次“生成三视图”；但只写剧本/提示词、查询接口、恢复已有task_id或维护规则，不据此启动媒体生成。此视觉要求不改变仅说话角色才配声的规则，不修改历史已提交请求。本节是制作与提交审计要求，现有程序的路径/schema校验不能自动证明图片内容确为合格三视图，仍须实看及核对真实请求。

## 先判断剧本是否需要人物说话

1. 按当前剧本/分镜仅列出需要说话的角色，包括剧本已有的画外对白/人物旁白。不说话的人物跳过下面的配声流程，声音字段可空或省略。呼吸、呻吟、吼叫等非语言声按具体声音设计处理，不触发强制配置人物说话音色。不能因模板有voice字段而新增台词或非语言声。
2. 对需要说话的人物查询YAML。有已确认且文件哈希未变的声音直接复用；跨作品若需复用，应显式记录来源/复用关系，不按显示名字自动合并人物。
3. 无声音时登记待配置，记录影响镜头。继续完成当前已授权且不依赖声音选择的剧本、分镜、图片、三维预演、静默镜头、检查和剪辑准备。文案/图片本身的既有确认门槛仍适用；不以此绕过。
4. 根据已实看、已选定的人物图片和剧情提出音色设计：听感年龄、音高、质感、语速、气息、语言/口音、克制或爆发等。它是**创意配音方案**，不是从外貌推断真实声音。英文设计指令与中文说明分开；试听台词沿用作品语言，不因英文prompt规则翻译人物台词。
5. 优先使用用户给的音频或已有声音库；有经核实可用的声音设计入口时，可按当前制作授权生成候选试听，再将候选作为参考音色。现有AutoDL IndexTTS2需要现成样本，不能把图片或一段音色文字塞进`prompt_simple`。无可用入口/样本时把具体缺口记入队列，不假称已生成，不擅自安装大型模型或开新账号。
6. **独立工作全部完成后，只为剧本中需要说话且未配声的人物集中通知用户配置/试听**：给这些人物的图片引用、识别描述、可播放音频、建议和受影响镜头；有多个人一起交。可在准备阶段记录缺口，但不提前用一串问题打断工作。不能将“独立工作完成”报告成整片已完成。
7. 用户同意后，把人物ID、该声音文件SHA-256和真实确认消息记在`voice.approval`，状态改`approved`。更换文件内容或改绑人物必须重新确认；改显示名不使音色失效。未认可候选保持`audition_pending`，不能自动通过。
8. 自动接续依赖声音的已授权生成/对白合成/口型同步/混音与成片验收，不重复索要同一授权。声音未确认时只暂停这些依赖步骤；不能先用随机声线做付费说话视频再要求用户接受或为返工买单。试听通过不等于最终台词、口型、多角色声线都通过，成片仍需实际听音。

## 样本与真实接口

参考优先单说话人、干净人声、无BGM/其他人插话、无混响过重或削波、正常语速。建议先准备约5–15秒能体现音色的短片段；这是本地制作建议，**不是API已声明的硬限制**。实际格式、时长、文件大小和语言能力按具体入口核验，必要转换另存，保留源样本。先技术解码，再实际试听；哈希与ASR都不能代替听音。

- u24本次公开契约有`ref_audio_0/1/2`三个槽，MP3/WAV/FLAC；本地映射人物→声样→槽位，并在英文视频提示词中明确图中人物与声音槽的关系。没有结构化speaker_id字段，不能保证提示词就能稳定绑定多人的音色。三个槽也不表示任意三个人一定不串音。超过容量时调整已审方案或采用单人对白/后期路线，不伪造第四槽。
- IndexTTS2：`prompt_simple`是必需音色样本（字段名确为simple）；`prompt_text`为实际要说的话；`emo_ref_audio`仅是可选情感参考，不能取代音色绑定。情绪变化不创建新人物声音身份。空白默认音频不算配置完成。
- 怪物吼声、非语言呼吸等属于按需声音/音效设计，不自动要求用户配置人物说话音色。用户另行指定声音素材时可保留关联，但不能假定人类TTS支持任意生物叫声，也不给它硬加台词。
- 音频同步视频入口需要人物图与真实台词音轨，它用来做音画同步，不等于从图片创造声音，也不等同于普通u24音色参考。用于哪一镜需经过方案审计，不自动替换全片制作方式。
- titim本次无独立声音槽，其作者说明保留引导视频原声；首尾帧lightx2v也无音频槽。明确保留源声的任务沿用源声，不为了补档案给原片换配音；需要固定新角色声音时先完成源声定位/提取试听或设计可用的后期路线，披露口型和首尾控制限制。不能悄悄改模型或声称已给无槽接口传声样。
- 新增声音不恢复默认BGM。对白、音色参考、情感参考、配乐、环境音分别登记；继续遵守[对白与后期配乐](music-postproduction.md)。

## YAML与工具

人物模板：[`角色.yaml`](../../templates/short-drama/角色.yaml)。创建和查看队列：

```powershell
.venv/Scripts/python.exe tools/角色.py init projects/我的作品/project.yaml --id CHAR-01 --label 青衣女子
.venv/Scripts/python.exe tools/角色.py queue projects/我的作品/project.yaml
```

queue只读，不提交生成、不自动确认。只列`speech_usage: dialogue`且缺少有效声音确认的人物；`none`、`vocalization`、`unknown`或未填都不产生配声待办。该属性是当前剧本的说话用途摘要，剧本改变时同步更新；未核对只列剧本核对项，不能转成请用户配声。具体镜头以该镜的`speakers`为准，不让旧摘要遗漏新台词，也不因其他镜头有对白要求本镜出声。

新声音参考生成清单使用`voice_policy: {version: 1, project: project.yaml}`（project路径相对materials所在目录）。每镜`speakers: [CHAR-01]`只登记剧本要求说话的人物；无人说话（包括只有非语言声）为`[]`，尚未核对为`null`；`voice_bindings: {ref_audio_0: CHAR-01}`，同时在`reference_bindings`将同一槽绑定到实际音频asset ID。音频asset为`kind: audio, purpose: character_voice, required: false`，路径指向人物YAML所选文件。所有媒体输入仍由既有精确路径检查校验。

`materials check --shot <ID>`只将该镜头的角色声音作为声音门槛；其他镜头待试听的角色声音不阻断它，原有视觉素材前置规则保留。全清单检查会列出全部待办。提交前还按当前真实API规则验证槽位。此自动门槛覆盖“每人独立音频参考槽”的路线；原声继承/多轨混音需按上节另留带源文件哈希的人工审计，不伪造音频槽来套模板。

历史已提交清单不自动补这个生产门槛，不改剧本哈希、不批量重生成；已有task_id恢复保持原契约。恢复后新做人物说话镜头时先补人物档案、声音路线与试听记录。新增档案时没有已确认的声音可保留空值或未配置，这本身不是待办；仅在剧本需要该人物说话时检查声音，不从已有成片擅自推定通过。
